# Architecture

Motix is a browser extension that restyles [Movix](https://github.com/movixstream/MovixOpenSource) from the outside. It has no access to Movix's build, so everything below is about doing that reliably against a site that changes without notice.

## The problem

Movix has no theming system. Its colours are hard-coded Tailwind utilities: about 13,000 uses of 1,200 distinct colour classes in the source, compiled to rules such as

```css
.bg-red-600 { background-color: rgba(220, 38, 38, var(--tw-bg-opacity, 1)) }
```

There are no CSS variables to override, and the public repository lags behind what is deployed: classes used on the live site (`.media-color-card`, for one) do not exist in it. The deployed stylesheet is therefore the only reliable description of the site.

## The approach: a generated adapter

```
live Movix stylesheet ──pnpm sync:upstream──▶ src/theme/generated/adapter.css   (static, shipped in the manifest)
                                              src/theme/generated/tokens.json   (the colours it found)

theme ──src/theme/palette.ts──▶ value for each token ──src/theme/theme-css.ts──▶ one small <style> per page
```

1. **`scripts/lib/build-adapter.ts`** parses the live stylesheet and, for every rule that sets a colour, emits the same selector with the colour replaced by a custom property that falls back to the original:

   ```css
   html[data-motix-theme] .bg-red-600 {
     background-color: rgba(var(--mx-bg-220-38-38, 220,38,38), var(--tw-bg-opacity, 1)) !important
   }
   ```

   Selectors are copied verbatim, so `hover:`, `group-hover:`, responsive and arbitrary-value variants are covered without anyone listing them. A token is named after its usage and its source colour: `bg-`, `fg-`, `bd-` (borders, rings) or `sh-` (shadows). Border radii get the same treatment through `--mx-radius-scale`.

2. **`src/theme/palette.ts`** decides what each token becomes for a given theme:

   | Source colour | Themed as |
   | --- | --- |
   | Neutrals (black, white, Tailwind grays and slates) | A ramp through the theme's background → surface → card → border → muted → text, by lightness |
   | Movix's brand red | The theme accent, keeping the shade (lighter reds become lighter accents) |
   | Everything else (success green, warning yellow, third-party brand colours) | Left alone |
   | Neutral shadows | Left alone, so shadows stay dark on every theme |

3. **`src/theme/theme-css.ts`** writes those values into one `<style>` element, plus the few rules a colour remap cannot express (poster cards tinted by inline variables, section titles styled by `<style>` blocks Movix injects at runtime, readable text on the accent colour, button size, and the grid that lights up under the pointer, which Movix paints in red on a canvas and Motix recolours with a `hue-rotate` filter).

Because every token falls back to its original colour, two things come for free:

- **The adapter is inert.** Without `data-motix-theme` on `<html>` it matches nothing; with it but no values, every rule resolves to Movix's own colour.
- **Scoped opt-outs.** Setting a token to `initial` restores the original colour for a subtree. The video player uses this for every token, and text laid over artwork (hero banners, poster cards) for the neutrals.

### When Movix changes

`.github/workflows/sync-upstream.yml` runs both sync scripts daily and opens a pull request if the output changed. New utility classes are picked up automatically; only the hand-written rules in `theme-css.ts` can go stale. `pnpm preview:live` screenshots the real site with a few themes for a human to review.

## Supported domains

`src/shared/domains.json` is generated by `pnpm sync:domains` from Movix's official directory, <https://movix.online/address.json> (the `active` list). It is the only place domains are written down: `src/shared/domains.ts` reads it at runtime and `scripts/lib/manifest.ts` generates both browser manifests from it.

A browser cannot grant an installed extension access to a new domain without a new version, so there is deliberately no "refresh domains" button: a new domain means a sync pull request and a release. The directory's `fake_domains` list is saved to `tests/fixtures/` and used as negative test cases.

## Runtime pieces

| Path | Role |
| --- | --- |
| `src/content/content-script.ts` | Runs at `document_start` on Movix domains. Reads settings, sets or removes the theme, re-applies on storage changes, and embeds the editor on `/themes`. |
| `src/content/route-detector.ts` | Detects SPA navigation. Content scripts live in an isolated world and cannot see the page's `history.pushState` calls, so this uses the Navigation API, with polling as a fallback. |
| `src/ui/popup/`, `src/ui/editor/` | The toolbar popup and the theme editor (React). They only write to storage. |
| `src/shared/storage.ts` | Settings in `storage.local`, with a migration that normalises anything it reads. |
| `src/theme/validation.ts` | Schema checks for imported themes and the allowlist for custom CSS. |

There is no background script and no message passing: the UI writes settings, and every open Movix tab reacts to the storage change event. The extension needs only the `storage` and `activeTab` permissions.

## Known limits

- **Inline styles.** Colours set through `style="…"` attributes (a few hundred places in Movix) are out of reach of a stylesheet.
- **Runtime `<style>` blocks.** Several Movix pages inject their own CSS when they mount. Only `.section-title` is handled, by hand.
- **Red means two things.** Movix uses the same red for its brand and for errors, so both follow the accent.
- **The player and artwork scopes are heuristics.** Movix has no single player root; the selectors in `theme-css.ts` cover what exists today.
- **Firefox is linted, not driven.** Playwright cannot load an extension into Firefox, so the browser tests run in Chromium only.
